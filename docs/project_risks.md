# 專案可能失敗的原因與排除

更新：2026-10-19。使用者：「評估後續這個專案可能會失敗的原因，給予排除。」

做法：先假設一年後這個專案失敗了，回頭列出最可能的原因；每一條都對照專案現在的實際狀態查證（程式、排程、資料、紀錄），再寫怎麼排除。狀態分三種：**已排除**（做完、有證據）、**這輪排除**（2026-10-19 做的）、**要你決定**（牽涉需求、花錢、系統設定或要你本人操作）。依「影響 × 發生機率」排序。

## 1. 升 T0 的路是斷的（這輪排除）

- **證據**：T0 要「前向觀察滿 60 個交易日、不輸 0050」（`daily.FORWARD_SESSIONS`）。但每月滾動（使用者 2026-10-16／10-17）規定前向帳戶一律從截止日隔天起算、每個月換一次：10 月從 9/1 起，到 10 月底大約 40～45 個交易日；11 月又改從 10/1 起。照現在的設計，**沒有任何規則會升成 T0**。路線圖日期表「2026-12-28 第一批滿 60 個交易日」那一列已經失效（帳戶已經改成 9/1 起，而且每月重算）。
- **建議的排除做法：串接的滾動前向紀錄**。每個交易日只算在「用前一個月底截止挑出來的名單」上：9 月的交易日看截止 8/31 的名單（10 月挑），10 月的交易日看截止 9/30 的名單（11 月挑），依此類推。一個規則連續留在名單上的月份串起來，每一天都是挑選時沒看過的資料。滿 60 個交易日（約 3 個月）且不輸 0050，就升 T0。這和「每月滾動、只用截止日以前的資料挑」完全一致，也不用改帳戶從截止日隔天起算的規定。
- **使用者 2026-10-19 選了這個做法**，已改：`stock_forward.chain`（手算測試）、選手池的等級改看串接紀錄（「串接前向 N／60 個交易日」）、需求與路線圖判定準則。從 10 月名單的前向起點 9/1 起算的第 60 個交易日是 **2026-11-30**（10/23 前寫成從 10/1 起算的 12/28、12/29，把 9 月的前向丟掉，使用者 10-23 指正），連續在 10～12 月名單上的規則最快那天收盤後升 T0。10/19 時 113 個名單上的規則各有 11 個交易日，105 個暫時不輸 0050。

## 2. 研究成果沒有變成你的實際投資（要你決定）

- **證據**：真實下單永久關閉是對的，但連「每月 5 日照哪個規則、買哪幾檔」的建議都還沒接到今日頁。S10 等你同意需求，而且要先有 T0，又被第 1 點卡住。
- **排除做法**：(1) 先決定第 1 點；(2) 從取捨前緣挑 1～2 個你能接受的規則（錢多：#4941、#4589；兼顧：#4938、#4940），前向帳戶已經在算，等於紙上實盤；(3) 同意 S10，讓今日頁每天給出這個規則的買賣清單，由你自己下單。

## 3. 回測數字被高估（已部分排除）

- **已排除**：每個試驗都登錄在雜湊鏈、不能刪改；新研究只用 2015-06～2020-09 挑；每月滾動只用截止日以前的資料挑，截止日之後是前向測試；前向帳戶逐筆照台股規則記錄並對帳；穩健性檢查（成本加倍、晚一天成交）放在研究總覽。
- **還要做到的**：把回測的超額報酬當上限看（大概打對折）；升 T0 只看前向證據（第 1 點）；不再加只差一點參數的變體（使用者 10/04 規定，持續遵守）。

## 4. 台積電獨強時落後 0050（已部分排除）

- **證據**：規則一律 100% 個股、每檔等額，不能放 0050，也不能照市值複製（使用者 10/09）。所以台積電獨漲的年份一定會落後，而且可能落後很久。
- **已排除**：研究總覽「跌市時的表現」列出每個規則「相對 0050 最大落後」與大跌時多跌多少，「前緣」讓你挑跌市穩的規則（#4940 最多只多跌 1.1 個百分點）。
- **你要事先知道的**：就算是最好的規則，也會有一整年輸 0050 的時候。照規則做下去，才看得到長期的結果。

## 5. 資料只有一份（這輪排除；異地要你決定）

- **證據**：每日 03:00 的資料庫備份（7 份）放在 `instance/backups/daily`，和資料庫在同一顆 C 槽；`instance/research`（試驗登錄、4,964 份報告、前向紀錄、每月名單、模型、歷史行情）完全沒有備份。
- **這輪排除**：`research/mirror.py`，worker 每晚 03:30 把研究資料（不含可重算的搜尋暫存、日誌）與最新的資料庫備份複製到 `RESEARCH_MIRROR_DIR`（設為 `D:\StockResearch-backup`，D 槽是另一顆實體硬碟）。只複製有變的檔案、那邊不刪檔；另外每晚打包試驗登錄、前向紀錄與每月名單，保留 30 天（壞掉的檔案被複製過去，也能拿前一天的回來）。
- **要你決定**：異地備份（房子出事、整台電腦壞掉）——例如雲端硬碟資料夾，給我位置就接上。

## 6. 服務停擺、出錯沒人知道（要你決定）

- **證據**：Windows 排程工作 `StockResearchLocalServices` 只在登入時觸發（互動式）、沒有自動登入；最近一次開機是 10/14 04:32（Windows 更新）。重開機後到你登入以前，盤後資料、前向紀錄都不會跑（開機後會補跑當天的流程、前向紀錄會補記，所以通常不會漏資料，但會晚）。失敗通知走 LINE，還沒設定，所以出錯只有打開網站才看得到。
- **排除做法**：(1) 使用者 10/19 決定自己改排程，步驟：
  1. 開始功能表搜尋「工作排程器」並開啟 → 左邊「工作排程器程式庫」→ 找到 `StockResearchLocalServices`，按右鍵「內容」。
  2. 「一般」分頁：選「不論使用者登入與否均執行」；不要勾「不儲存密碼」（要能讀你的使用者資料夾）。
  3. 「觸發程序」分頁：「新增」→「開始工作」選「啟動時」→ 勾「延遲工作的時間」選 1 分鐘 → 確定（原本的「登入時」留著）。
  4. 按「確定」，輸入你的 Windows 密碼（只有你本人輸入）。
  5. 改完跟我說，我用 `scripts\start-services.ps1` 重新啟動並確認健康檢查；下次重開機後我會看 `instance\supervisor.log` 是否在登入前就啟動。
  (2) 建立 LINE 官方帳號（S5-W07，`docs/line-notifications.md`）。

## 7. 成本與成交（已部分排除）

- **已排除**：引擎逐筆照台股規則（漲停買不到、跌停賣不掉、整股與零股、最低手續費、成交量參與上限），10/16 稽核 429,149 筆 0 違規；成本加倍檢查；R4 盤後零股成交率。
- **2026-10-21 重新稽核**（引擎 1.5.0）：10/17 的稽核標出 452 筆「收盤鎖漲停還買」、122 筆「鎖跌停還賣」，查證是稽核程式把「隔天開盤成交」的委託用收盤價判斷、組合帳戶整個套用「當天盤後」的委託量上限、停牌或減資後復牌當天用前一天收盤算範圍，都是稽核的誤判（交易引擎本身沒改）。修正稽核後重跑：542 個規則、3,154,487 筆委託，**0 違規**（`audit/trade-audit-20261021-113926.json`）。之後每週日 06:00 自動稽核，每天 16:00 的需求檢查核對最新一次 0 違規、8 天內。
- **還要做到的**：S10-W03（你沒買到時，依實際持股調整之後的單，等你同意）；開始照規則下單後，記錄實際成交價回來和模擬比。
